# Mediquest の Codex 直接開発

2026-10-31 のユーザー指示により、TAKT 経由の開発を終了し、Codex が直接実装・検証する。対象は `takechiyo-19940627/mediquest`、実用側 `app/`。初回リリースの機能完成を優先する。

Issue作成、実装、失敗改善、レビュー対応、条件を満たすPRのマージは承認済み。定期実行・heartbeatは再開しない。現在の依頼の範囲で作業を継続し、無関係な新機能で仕事を増やさない。

## 役割

- `roles/planner.md`: 合意済み要件と既存実装から次の作業を絞る。
- `roles/dispatcher.md`: 作業ツリー・担当・依存・競合を管理する。
- `roles/maintainer.md`: 不具合・環境問題を調査し修正する。
- `roles/reviewer.md`: 実装とは別コンテキストで差分と検証結果をレビューする。
- `roles/integrator.md`: 最新headのCIとレビューを確認し、条件を満たすPRをマージする。

監督者が複数の役割を担当してよいが、実装と承認レビューは分ける。独立した調査・レビューにはサブエージェントを使う。

## 手順

1. リポジトリ、ブランチ、未コミット変更、既存Issue/PRを確認する。中断済みの成果を保全し、同じ修正の重複作成を避ける。
2. 受け入れ条件と最小の実装範囲を確認し、専用の作業ツリーで直接編集する。小さな修正には長い計画書や実行基盤の整備を必須としない。
3. 変更に対応する回帰テストを実行し、アプリ変更では全7品質ゲートを実行する。結果と対象コミットを記録する。
4. 別のエージェントが実差分・受け入れ条件・検証結果をレビューし、指摘を修正する。
5. 既存PRの修正は同じブランチへpushする。必要CI・最新headの独立レビュー・未解決指摘なしを確認してマージする。
6. 結果、残課題、次に必要な対応を報告する。未実行や失敗を成功扱いしない。

## 実行上の制約

- 独立した実装は最大2件。同一checkoutの編集・ビルドを競合させない。ユーザーの作業を切替・上書きしない。
- 同じ失敗を根拠なく再試行しない。原因を修正して必要な検証を再実行する。外部認証・利用制限などで進めない場合は具体的な対応を伝える。
- TAKTのqueue、retry回数、workflow、プロバイダー起動ラッパーは直接開発の実行条件にしない。旧タスクを再投入したり、履歴をリセットしたりしない。
- 旧 `.takt/supervisor/` の履歴と旧作業コピーは調査資料として保全する。今後の証拠はPRと必要に応じたローカルログに残す。秘密情報は保存しない。
- 他のClaude/Codexプロセスを勝手に終了しない。権限・認証の回避や品質基準の緩和で完了にしない。
- 無期限常駐や将来の自動実行は約束しない。定期実行を追加・再開する場合は別途明示指示が必要。
