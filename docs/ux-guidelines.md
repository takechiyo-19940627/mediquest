# 実用アプリの UX 方針

対象は `app/`。本資料は採用済みの方針であり、実装済みを意味しない。実用側の操作について旧 [要求定義](requirements.md) と異なる場合は、本資料を優先する。

## 基本方針

学習を中断しても戻れること、AI の結果を確認できること、失敗してもやり直せることを重視する。管理者の教材作成と学習者の演習を分ける。

## 管理者による教材・問題の提供

- 教材の登録・編集、文字起こし内容の確認、AI 問題生成は管理者ページで行う。管理者が提供内容に責任を持つ。
- 生成直後の問題は下書きとする。管理者が内容を確認し、必要な修正をしてから明示的に公開する。自動公開しない。
- 学習者には公開済みかつ出題停止されていない問題を提供する。演習開始時に問題生成を待たせない。
- 教材がない管理者には登録を案内する。利用可能な問題がない学習者には未提供であることを伝え、教材登録に誘導しない。
- 管理者が採用する問題を選び、問題セット単位で公開する。具体的な一括確認 UI は画面実装時に詰める。

## 演習と再開

- サーバー指定の必要選択数を使い、「1 つ選べ」「2 つ選べ」や3つ以上の場合も「選択 → 回答する」で確定する。必要な選択数を明示し、確定前は選び直せる。旧要件の単一選択時の即判定は採用しない。
- 確定後は回答を書き換えず、正誤・正答・解説・根拠引用を確認できるようにする。自動で次へ進めず、利用者が「次へ」を押す。
- 確定した回答は都度サーバーに保存し、保存中・保存済み・失敗を区別する。失敗した状態を保存済みとして表示しない。
- 演習を中断しても、保存済みの進捗を使って次の未回答問題から再開できるようにする。再開で回答済み問題を重複記録しない。
- 正誤や保存状態は色だけに頼らず文字やアイコンでも伝える。
- 結果から間違えた問題の復習へつなぐ。初期は連続学習日数などで継続を迫る設計を導入しない。

## 待機と失敗からの回復

- 管理者の AI 処理は「文字起こし中」「問題を生成中」など、実際に把握できる段階を表示する。不明な残り時間や進捗率を作らない。
- 失敗時も入力済みの教材を保持し、再入力せずに再試行できるようにする。
- 連打や同じ操作の再送で問題・解答履歴を重複作成しない。処理状況が不明な場合は失敗と断定せず、状態確認と再試行を区別する。
- 生成の `running` はサーバー停止後にも残り得るため、実行中である保証として表示しない。記録済み状態・更新時刻と状態確認操作を提供する。応答喪失時は同じ受付キーを使用し、新しい生成は追加課金の可能性を説明した明示操作でのみ開始する。旧受付・教材を残し、遅れて完了した旧結果と新しい結果を混同しない。

## 根拠の表示と問題の不備

- AI の解説と教材からの引用を明確に分ける。引用の一致は正解の妥当性の保証として表示しない。
- 学習者は解説付近から不備を報告できる。報告だけで全員の出題・成績を変更しない。
- 報告者本人は対象問題を一時的にスキップして学習を続けられる。スキップを誤答として新規記録しない。
- 管理者が報告を確認し、不備を確定した問題を出題停止し、正答率などの集計から除外する。既存の解答履歴は削除せず、不備による除外と分かるようにする。
- 管理者が修正・再検証を行う。初回の再検証は内容確認と引用再照合であり、別のAI再判定呼出しは含めない。公開済み問題の版を残し、修正前の解答は当時の問題・正解にひも付ける。通常の改訂で過去の成績を再採点しない。不備確定による集計除外は理由を明示する。
- 公開・改訂・再開の具体案は [画面一覧・DB設計](screens-and-data-model.md) を参照する。
