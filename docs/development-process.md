# Codex による初回リリース向け開発

2026-10-31 更新。ユーザー指示により、実用側 `app/` は Codex が直接実装・検証する。TAKTによる投入・実行・復旧を開発手順から外し、機能完成に集中する。定期実行は再開しない。

## 基本方針

合意済みの技術・UI・UX・DB方針を基準に、小さな変更を実装、検証、独立レビュー、PRの順で届ける。小規模な修正に大きな計画書やオーケストレーター整備を要求しない。既存Issue/PRを優先し、新しい作業を重複作成しない。

実装と承認レビューは別のエージェント・コンテキストで行う。AIの完了宣言だけで承認せず、差分と実行結果で確認する。役割とマージ条件は [agents/AGENTS.md](../agents/AGENTS.md) に従う。

## 作業の進め方

1. Issueの目的・対象外・受け入れ条件（AC）と既存PR・差分を確認する。大きい機能は確認可能な縦の単位に分ける。
2. 専用作業ツリーの `codex/` ブランチでCodexが直接編集する。既存PRの修正は同じブランチへ反映する。ユーザーの未コミット変更を上書きしない。
3. 必要な回帰テストを追加し、アプリ変更では以下の全7ゲートを実行する。失敗した原因を修正して再検証する。
4. 独立レビューでAC、権限、DB、UX、テストの妥当性を確認する。指摘解消後にpushし、最新headのCIを確認する。
5. 独立レビュー、必要CI、未解決指摘なしを満たしたPRを条件付きでマージする。未完了の共有はDraftとして区別する。

実装は最大2件まで並列化できる。ファイルやDB契約が競合する作業は直列にする。同じcheckoutで編集・ビルドを競合させない。権限・データ消失・公開範囲など仕様の重大な変更は勝手に追加しない。

## ローカル検証とCI

Nuxt本体、アプリの検証コマンド、`App checks` と `Process checks` のCIは導入済み。ブランチ保護・rulesetの実設定はマージ時に確認し、文書だけで強制されているとは扱わない。

アプリは `app/.node-version` と `app/package.json` の固定版を使用する。現在のmacOS環境ではNode 24.15.0とnpm 11.12.1。ローカルではリポジトリ直下から次を直接実行する（TAKTは不要）。

```sh
bash scripts/app-command.sh ci
bash scripts/app-command.sh browser:install
bash scripts/app-command.sh quality
```

`app-command.sh` は既存nodenvを使い、この実行だけ固定版を選ぶ。nodenvのない環境では指定版のNode/npmを用意し、`npm ci --prefix app`、`cd app && npm exec -- playwright install chromium`、リポジトリ直下の `node scripts/check-app.mjs` を使用する。Linux CIではブラウザのOS依存も `--with-deps` で準備する。

`quality` / `check-app.mjs` は次を順に実行する。一つでも失敗すれば未完了であり、存在しないチェックや未実行を成功扱いしない。

| ゲート | 内容 |
|---|---|
| `format:check` | 整形差分 |
| `lint` | 静的解析 |
| `typecheck` | Nuxt/Vueを含む型検証 |
| `test:unit` | 採点・公開条件などのルール |
| `test:integration` | SQLite、権限、再送、版と履歴などの結合検証 |
| `test:e2e` | ブラウザからの主要導線 |
| `build` | 本番用ビルド |

アプリCIは同じ `scripts/check-app.mjs` を実行する。Process checksの成功だけでアプリ検証を代替しない。文書のみの変更では無関係なローカルアプリ検証を必須としないが、GitHubの必要チェックは維持する。

UI変更ではライト/ダーク、スマホ/PC、キーボード、空・失敗状態を確認し、画面証拠を残す。自動アクセシビリティ検査と目視を併用する。画像比較は合意した基準画面に対して行い、画像の自動更新だけで差分を承認しない。DB変更では新規作成と既存データの移行・履歴保持を確認する。テストで実APIキー・本番DB・実データを使用せず、通常CIのAI APIは固定応答にする。

テスト・CI・品質設定・開発手順の変更は実装者以外がレビューする。期待値を下げる、必須チェックをskipする、保護を迂回するといった方法で完了にしない。

## 検証で守る重要な仕様

- 管理者以外は教材登録・生成・公開・不備確定APIを操作できない。
- 未公開問題・他人の履歴・回答前の正解を取得できない。
- 回答の再送・連打で記録が増えず、確定済み回答を書き換えられない。
- 中断・再開で出題順と確定済み回答が保持される。
- 問題改訂後も過去の解答は当時の版を参照する。
- 不備確定時は履歴を消さず集計から除外し、対象0件は0%と表示しない。
- 生成失敗後に教材が消えず、同じ受付の再送で生成処理を重複開始しない。

これらを該当機能の受け入れ条件とテストに落とす。テストを通す目的で期待値を弱めたり、失敗テストを削除・skipしたりしない。仕様変更に伴う期待値の変更は理由をPRに示す。

## PRとマージ

PRには関連Issue、変更理由、ACに対応する検証結果、画面・移行の証拠、未確認事項を記載する。コード変更後は検証と独立レビューを最新差分に対して更新する。GitHub CIはpush後のマージ条件であり、push前に待つ循環を作らない。

マージ直前に最新head、必要CIの成功、独立レビュー、未解決指摘なし、競合なしを再取得する。人のCHANGES_REQUESTEDを独立AIレビューで上書きしない。head SHAを固定し、管理者バイパスやブランチ保護の解除を使わない。詳細は [マージ担当](../agents/roles/integrator.md) を参照。

## 旧TAKT運用の扱い

`.takt/`、旧ラッパー、修復コード、旧作業コピーは過去の調査資料として保全する。旧queueやretry回数はCodex直接開発の実行条件ではない。キューを更新・リセットしたりTAKTを再起動したりしない。TAKTを使うことを前提とした古いIssue本文や記録より本方針を優先する。

既存の品質ゲートとCIは継続する。Process checksに残るTAKT関連の回帰試験は履歴保全のため維持しており、実開発でTAKTを起動することを意味しない。不要コードの削除は別の明示的な整理作業とする。

定期実行・heartbeatは停止を維持する。別のClaude/Codexプロセスを勝手に終了しない。必要な外部対応がある場合は、失敗原因と再開条件を具体的に報告する。
