# 実用アプリの技術方針

合意日: 2026-10-24

## 目的と利用者

Rust 学習とは独立して、問題演習アプリを早く実用化する。当面は本人のみが利用し、将来は友人にも使ってもらう程度を想定する。
機能要件は [requirements.md](requirements.md) を参考にする。実用側の技術方針は本資料を優先し、旧資料の Rust 前提の構成は引き継がない。

## 管理者と学習者の役割

- 教材の持ち込み・登録は管理者のみが行い、管理者ページに配置する。
- 教材からの AI 問題生成も管理者のみが実行し、生成内容の確認と提供する問題の品質に責任を持つ。学習者には教材登録・問題生成の操作を提供しない。
- 学習者は管理者が用意した問題で演習し、自分の解答履歴を確認する。当面は本人が管理者と学習者を兼ねる。
- 友人への提供時は管理者と学習者の権限を分け、管理用 API でも権限を検証する。画面の表示制御だけに依存しない。
- 教材・問題は管理者が管理する共有コンテンツ、解答履歴は利用者ごとのデータとして区別する。旧要求定義の一律の `user_id` をそのまま所有者・閲覧権限の意味には使わない。
- 生成問題は下書きにし、管理者が確認・修正してから公開する。学習者の不備報告は管理者が確認し、不備確定後に出題・集計から除外する。詳細は [UX 方針](ux-guidelines.md) を参照する。

## 初期版の範囲

テキスト教材登録から AI 生成、管理者確認・セット単位の公開、演習・履歴・再開までを優先する。画像の文字起こしは次の段階とする。初回は演習ごとの結果・本人の履歴を提供し、旧要求定義のAIによる正解再判定や全体・教材別の横断成績集計は含めない。品質確認は管理者による確認修正、引用照合、不備判断、改訂で行う。画面とデータの設計案は [画面一覧・DB設計](screens-and-data-model.md) を参照する。

## 採用方針

- フロントエンド: Nuxt / Vue + TypeScript。
- UI ライブラリ: Nuxt UI。
- AI は Anthropic API から始め、モデルはサーバー設定で変更可能にする。複数社対応は後回しにする。
- バックエンド: 同じ Nuxt プロジェクト内のサーバー機能。実行環境は Node.js。
- 画面から教材・問題・履歴の読み書きや問題生成を API 経由で行う。
- API の入口と、問題生成・引用照合・保存の処理を分ける。
- AI API キーはサーバー側のみで扱う。キーや DB 接続設定は環境変数で設定し、PC 固有のパスをコードに埋め込まない。
- Go による独立バックエンドは現時点では導入しない。
- DB は SQLite、DB アクセスは Drizzle ORM、マイグレーションは Drizzle Kit を採用する。

## デザイン方針

共通部品・レイアウト・操作・確認のルールは [UI ガイド](ui-guidelines.md) を参照する。

- メインカラーは落ち着いた青緑（ティール）。主要ボタンや選択中の項目に使用する。
- ライト・ダークの両テーマに対応する。旧要求定義のダークテーマのみを前提とした方針より、本方針を優先する。
- ライトテーマは白に近いグレーの背景と濃いスレートの文字を基本とする。
- ダークテーマは濃いスレート系の背景と明るい文字を基本とし、ティールの明度を背景に合わせて調整する。
- 注意・要確認にはアンバーを使う。赤はブランドカラーにせず、エラーなど必要な箇所に限定する。
- ブランドカラーと正誤の意味を分ける。正解・不正解は色だけに頼らず、アイコンと文字を添える。
- 両テーマで本文・解説の読みやすさ、選択状態やフォーカスの見分けやすさを確認する。具体的な色値は画面実装時に調整する。

## 利用環境と展開順序

1. 自分の PC 上で Web アプリとして利用する。
2. 必要になれば Node.js を実行できるリモートサーバーへ移す。
3. 必要になれば Capacitor / Tauri によるアプリ化を検討する。いずれも現時点では未採用。

アプリ化時は Web の画面を活用し、サーバー処理はリモートの Nuxt API に残す構成を基本案とする。Nuxt のサーバー処理をそのまま端末へ同梱する前提にはしない。

## データ保存と運用

- 教材・生成問題・解答履歴はサーバー側の SQLite に保存する。ブラウザ側の保存領域を正本にしない。
- 利用者 ID を最初から持たせる。本人利用中は固定ユーザーとし、友人への提供時に認証と利用者ごとのアクセス制御を追加する。
- 教材画像は文字起こし後に保存せず、管理者が確認・修正したテキストを保存する。
- AI の応答待ち中は DB のトランザクションを開かず、生成結果を検証してから短いトランザクションで保存する。
- テーブル定義は TypeScript で管理し、Drizzle Kit で変更用 SQL を生成する。SQL を確認して Git に記録し、マイグレーションとして適用する。
- DB ファイルは Git 管理外とし、保存先は環境変数で指定する。実データを蓄積する段階でバックアップ・復元手順を整える。
- リモート移行時も、まず永続ディスクを持つ単一の Node.js サーバーで SQLite を利用する。DB ファイルを一時的な実行領域に置かない。
- 複数サーバー構成や同時書き込みの増加が必要になった場合は PostgreSQL を再検討する。変更時はスキーマ・クエリの見直しとデータ移行が必要で、接続先の変更だけでは済まない。

## 実装の進め方と品質保証

[開発プロセス](development-process.md) を採用する。Issueで範囲と受け入れ条件を定め、Codexが直接実装・機械検証を進め、別のエージェントがレビューする。型・Lint・テスト・ビルドをCIでも実行し、証拠を添えたPRを独立レビューし、監督者が条件を確認してマージする。詳細は [自律運用](../agents/AGENTS.md) を参照する。
Nuxt基盤、検証ゲート、アプリCIは導入済み。必須チェックの保護設定はマージ時に実設定を確認する。TAKTの運用は終了し、定期実行は再開しない。

## 実装済みと残る判断

SQLiteはbetter-sqlite3とDrizzleを使用し、スキーマ・移行とバックアップ/復元CLIを実装済み。依存版は `app/package.json` とlockfile、操作手順は [app README](../app/README.md) を参照する。API実装済みを画面完成や受入完了とは扱わない。残る実装は [初回リリース計画](first-release-plan.md) で追跡する。

以下は画面実装時または後続段階で具体化する。

- 公開・改訂・再開の具体的な画面操作（[画面一覧・DB設計](screens-and-data-model.md)を基準に実装時に具体化）
- 友人にも提供する段階の認証方式
- リモートサーバーの選定、デプロイ方法、Docker 導入の要否
- アプリ化の要否と対象 OS、オフライン演習・同期の要否
